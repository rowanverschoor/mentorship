# Weather App

Enter a latitude and longitude, click a button, see the weather.
Angular frontend + C# (.NET 8) backend, which calls the API Ninjas weather API.

## Run it

```bash
dotnet user-secrets set "ApiNinjas:Key" "<your key>"   # once, inside backend/WeatherApi
./run.sh                                               # starts both
```

- Frontend: http://localhost:4200
- Backend: http://localhost:5149/weather?lat=52.37&lon=4.89

## How a request flows

```
Browser (Angular, :4200)
  → WeatherService.get()          HTTP GET /weather?lat&lon
  → C# endpoint (:5149)           Program.cs
  → IWeatherService               interface
  → ApiNinjasWeatherService       calls api.api-ninjas.com, maps JSON → WeatherResult
  ← WeatherResult as JSON
  ← Component shows it
```

## Backend (`backend/WeatherApi`)

| File | Job |
|---|---|
| `Program.cs` | Wiring only: registers services, enables CORS, defines `GET /weather` |
| `Models/WeatherResult.cs` | Our own response shape (not API Ninjas') |
| `Services/IWeatherService.cs` | Contract: "get weather for a location" |
| `Services/ApiNinjasWeatherService.cs` | The one class that knows about API Ninjas |
| `appsettings.Development.json` | Allowed CORS origin |

The API key lives in user-secrets, not in the code or git.

## Frontend (`frontend/src/app`)

| File | Job |
|---|---|
| `models/weather.ts` | `Weather` interface: shape of the backend's JSON |
| `config.ts` | Backend URL, in one place |
| `services/weather.service.ts` | The only code that does HTTP |
| `app.component.ts` | UI: two inputs, a button, shows the result |
| `app.config.ts` | App-wide providers (`provideHttpClient()`) |

## What Angular gave us vs. what we wrote

**Generated by `ng new`:** `package.json`, `angular.json` (build/serve config),
`tsconfig*.json`, `src/index.html` (contains `<app-root>`), `src/main.ts`
(starts the app), and the empty `AppComponent` / `app.config.ts`.

**Ours:** everything in the two tables above except the generated shells.
We added `provideHttpClient()` to `app.config.ts` and filled in the component.

**How Angular starts:** `main.ts` → `bootstrapApplication(AppComponent, appConfig)`
→ the component with selector `app-root` replaces `<app-root>` in `index.html`.

## Angular concepts used

- **Component**: class + template. `imports: [FormsModule]` lists what the template needs.
- **Dependency injection**: `inject(WeatherService)` asks Angular for an instance.
  `@Injectable({ providedIn: 'root' })` makes the service available app-wide.
- **Data binding**: `[(ngModel)]` (two-way, inputs), `{{ }}` (class → screen), `(click)` (screen → class).
- **Observable**: `http.get()` does nothing until `.subscribe()`. Like a Promise that can be lazy.
- **`@if`**: shows a block only when its condition is true.

## SOLID: where it shows up

- **S**: each class has one job (endpoint, service, model; component, service).
- **O**: add a new weather provider by writing a new `IWeatherService` class; the endpoint doesn't change.
- **L**: any `IWeatherService` implementation can replace another.
- **I**: `IWeatherService` has one small method.
- **D**: the endpoint depends on `IWeatherService`, not on API Ninjas or `HttpClient`.
  The only place that names the concrete class is the registration in `Program.cs`.

## Things worth being able to explain

- **CORS**: the browser blocks `:4200` from reading responses from `:5149` (different origin)
  unless the backend allows it. Enforced by the browser, which is why curl works without it.
- **`Task` / `async` / `await`**: the C# way of waiting for slow work (network) without blocking a thread.
- **Why our own `WeatherResult`**: the frontend doesn't break if the upstream API changes or is swapped.
- **Why the `I` in `IWeatherService`**: .NET naming convention for interfaces (unrelated to the I in SOLID).
